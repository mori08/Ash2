# DOCUMENTATION.md

プロジェクト構造ドキュメント（ARCHITECTURE.md / REFERENCE.md）の更新ルール。

## 2つのドキュメントの分担

**ARCHITECTURE.md は全体の構成を説明する。** 何がどう組み合わさって動いているかを、初めて
このコードに触れる人が通しで読んで掴めるように書く。読み終えたとき、REFERENCE.md に並ぶ部品が
それぞれどこに差さるものか分かっている、という状態を目指す。

**REFERENCE.md は個々の部品を一覧する。** 目的の部品がどこにあり何をするかを、必要なときに
必要な行だけ引く。通読は想定しない。

| | 書くこと | 増え方 |
|---|---|---|
| [ARCHITECTURE.md](../ARCHITECTURE.md) | 部品が差し込まれる土台の構造 | 部品が増えても増えない |
| [REFERENCE.md](../REFERENCE.md) | 部品そのものの一覧（コンポーネント・システム・フェーズ・入力・アセット） | 部品が増えるたびに線形に増える |

読み方が違うため、分量の扱いも違う。ARCHITECTURE.md は通読できる長さに保ち（300行上限）、
REFERENCE.md には上限を設けない。

同じ事実を複数のドキュメントに書かない。

## ARCHITECTURE.md に書くかの判定

3つの基準を使う。**すべて満たしたものだけ**書く。

**基準1（量）— 部品を1つ足したとき、この記述は増えるか？**

増えるなら部品の話。REFERENCE.md へ。

**基準2（波及）— これを別の仕組みに置き換えたとき、どれだけ書き直すことになるか？**

全体に及ぶなら土台。1つの機能の周辺で収まるなら部品で、REFERENCE.md か
`docs/game_design/` へ。

| 例 | 置き換えたときの影響 | 判定 |
|---|---|---|
| フェーズ管理を `s3d::Scene` に替える | 全フェーズを書き直す | 土台 |
| 座標系の軸を変える | 位置を持つ全エンティティに及ぶ | 土台 |
| Motion の状態表現を替える | 全行動を書き直す | 土台 |
| 当たり判定の形状・判定方法を替える | 判定まわりに留まる | 部品 |

当たり判定のように「実装を進める過程で普通に変わる」ものは、たとえ広く使われていても
土台ではない。土台として書くのは、変わったら設計そのものが揺らぐものに限る。

**基準3（有効性）— 読者がこれから書くコードに効くか？**

| 種類 | 書くか |
|---|---|
| 何を選んだか | ○ |
| それが何を保証するか・何に使えるか | ○ |
| なぜ他の案を採らなかったか | ✗ その判断はもう済んでいる |

理由を残したい場合は、誘惑が生じるコードのすぐ隣に Why not コメントで置く
（[COMMENT.md](COMMENT.md)）。判断の経緯そのものは Issue と PR に残る。

## ARCHITECTURE.md の書き方

扱う土台は7つ（座標系・ECS・フェーズ・Motion・Config・入力・描画）。

**構造を説明する。用語の一覧にしない。** その仕組みが何を可能にしているかを先に書き、
型の名前はその中で自然に出す。「誰が何を知らないか」「どこに閉じているか」のように、
責任の所在が見出しだけで分かる形にする。

**呼び出しの連鎖は図で示す。** コード例より短く、本筋だけが残る。

```
Main.cpp ── registry を1つ作る
  └ PhaseStack::update(registry, frameData)
       └ IPhase::update(registry, frameData)    ← 先頭のフェーズだけ
            └ 各 System::Update(registry, ...)  ← そのフェーズに必要なものを順に
```

**呼び名はコードの識別子に合わせる。** ECS のように外部の標準語彙があるものはそれを使うが、
このプロジェクト固有の仕組みに新しい訳語を作らない。

**書かないもの。** 採らなかった選択肢とその理由、部品名の列挙、コードを書くときの注意、
文書自身についての説明（読み方・章立ての意図）。

### 300行上限

土台の説明は部品が増えても増えないため、行数が伸び続けるなら部品の話が混ざっている疑いがある。
上限は分量の目安であると同時に、その混入を検出するための仕掛けでもある。

超過しそうな場合は以下の優先順位で削る：

1. コード例（コードを見ればわかる）
2. 特定の部品1つにしか効かない説明（REFERENCE.md か `docs/game_design/` へ出す）
3. 実装の詳細（メンバ構成・分岐条件・評価順）
4. 現在使われていない設計の説明

削ってはいけないもの：7つの土台の構造・土台をまたぐ横断的な制約

**土台の章は安易に増やさない。** 新しい章を立てる前に、それが本当に差し込み口
（部品を足す人が必ず通る場所）かを判定する。

## REFERENCE.md の書き方

「何があるか」と「どこを見ればよいか」を引くためのドキュメント。一覧性を保つため、
原則としてテーブル形式で書く。

行数上限はないが、1エントリの説明を無制限に長くしてよいわけではない。
1つのテーブルセルに複数の関心事を詰め込みそうな場合は、詰め込まずに
以下の分担で別のドキュメントへ出し、REFERENCE.md には参照だけを残す。

| 内容 | 出し先 |
|---|---|
| ゲームデザイン上の仕様（区間の秒数・キャンセル可否・リアクション Lv など） | `docs/game_design/` 配下 |
| 土台の構造（部品が増えても変わらないもの） | ARCHITECTURE.md |
| コードを書くときの注意 | 「部品追加時の注意」の節、または `docs/coding_style/` |
| 実装の詳細（メンバ構成・分岐条件・評価順） | コードと Doxygen コメント |

テーブルの列に収まらない例外だけ、節末の箇条書きに残してよい。

### ファイルへのリンク

クラス・システム・フェーズなどを一覧するテーブルでは、名前をリポジトリルートからの相対パスリンクにすること。
リンク形式は `[ClassName](../Ash2/src/Path/To/File.hpp)`（`docs/` からの相対パス）。

リンク化するのはこの部品一覧テーブルの名前だけ。本文中でアセット・設定ファイルを
指すときは、リポジトリルートからの相対パスをバッククォートで書く
（例: `` `Ash2/App/assets/config/player.toml` ``）。ワイルドカードを含むパスは
リンクにできないため、この種のパスはリンク化せず表記を揃える。

## 更新のタイミング

以下の変更を行った場合、実装後・返答前に必ず該当ドキュメントを読み、
現状と乖離があれば更新すること。

**ARCHITECTURE.md を更新するケース**

- 土台そのものの変更（構成要素の追加・削除・役割の変更）
- ディレクトリ構成の変更
- 土台をまたぐ横断的な制約の追加・変更

**REFERENCE.md を更新するケース**

- コンポーネント・システム・フェーズ等の新規追加・削除・仕様変更
