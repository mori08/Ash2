# DOCUMENTATION.md

プロジェクト構造ドキュメント（ARCHITECTURE.md / REFERENCE.md）の更新ルール。

## 2つのドキュメントの分担

- [ARCHITECTURE.md](../ARCHITECTURE.md) — 設計意図（ディレクトリ構成・レイヤー構成・
  ゲームループ・座標系・主要な制約）。**200行上限**。
- [REFERENCE.md](../REFERENCE.md) — 個々の部品一覧（コンポーネント・システム・
  フェーズ・入力・アセット）。行数上限なし。機能追加のたびに
  線形に増える前提のドキュメント。

以下の変更を行った場合、実装後・返答前に必ず該当ドキュメントを読み、
現状と乖離があれば更新すること。

**ARCHITECTURE.md を更新するケース**

- ディレクトリ構成の変更
- アーキテクチャ方針の変更（フェーズ管理・ECS の使い方など）
- 座標系・ゲームループの変更

**REFERENCE.md を更新するケース**

- コンポーネント・システム・フェーズ等の新規追加・削除・仕様変更

## ファイルへのリンク

クラス・システム・フェーズなどを一覧するテーブルでは、名前をリポジトリルートからの相対パスリンクにすること。
リンク形式は `[ClassName](../Ash2/src/Path/To/File.hpp)`（`docs/` からの相対パス）。

リンク化するのはこの部品一覧テーブルの名前だけ。本文中でアセット・設定ファイルを
指すときは、リポジトリルートからの相対パスをバッククォートで書く
（例: `` `Ash2/App/assets/config/player.toml` ``）。ワイルドカードを含むパスは
リンクにできないため、この種のパスはリンク化せず表記を揃える。

## ARCHITECTURE.md の200行上限

超過しそうな場合は以下の優先順位で削る：

1. コード例（コードを見ればわかる）
2. 実装の詳細（How より Why を残す）
3. 現在使われていない設計の説明

削ってはいけないもの：レイヤー構成・座標系・主要な制約・設計の意図

## REFERENCE.md の記述ルール

REFERENCE.md は「何があるか」と「どこを見ればよいか」を引くためのドキュメント。
一覧性を保つため、原則としてテーブル形式で書く。

行数上限はないが、1エントリの説明を無制限に長くしてよいわけではない。
1つのテーブルセルに複数の関心事を詰め込みそうな場合は、詰め込まずに
以下の分担で別のドキュメントへ出し、REFERENCE.md には参照だけを残す。

| 内容 | 出し先 |
|---|---|
| ゲームデザイン上の仕様（区間の秒数・キャンセル可否・リアクション Lv など） | `docs/game_design/` 配下 |
| 設計意図（なぜその構造を選んだか） | ARCHITECTURE.md |
| 実装の詳細（メンバ構成・分岐条件・評価順） | コードと Doxygen コメント |

同じ事実を複数のドキュメントに書かない。テーブルの列に収まらない例外だけ、
節末の箇条書きに残してよい。
