# ERROR_HANDLING.md

エラー処理の規範。

## 1. 原則

- 失敗は値で伝える（`Optional<T>` / `std::expected<T, E>`）
- 終了を決めるのは、失敗を受け取った側
- `try-catch` は `Main()` と、外部 API を変換する関数にのみ書く

`Optional` / `expected` を返せる関数の中では終了を決めない。
判定は「この関数は `Optional` / `expected` を返せるか」で行う。

## 2. 失敗に気づいたとき

取る手段は `assert` と戻り値の2つ。

- `assert(条件 && "日本語メッセージ")` — コードが正しければ起きない失敗（不変条件・呼び出し契約の
  違反）。外部入力・設定ファイル・ユーザー操作の検証には使わない
- 戻り値 — `[[nodiscard]]` を付ける
  - `Optional<T>` — 「値がない」ことが仕様上の正常な結果
  - `std::expected<T, E>` — それ以外の失敗。`E` の既定は `String` で `U"関数名: 内容"` の
    形式。内容で分岐せず、分岐が必要なら `enum class` にする

## 3. 終了を決めたとき

`FatalError` を投げる。投げたあとは必ず終了し、回復されることはない。

```cpp
throw FatalError{
    .reason = FatalReason::AssetMissing,
    .detail = U"LoadClips: {} を開けません"_fmt(path),
};
```

- 分類は `FatalReason` から選ぶ。当てはまるものがなければ追加する
- `detail` は開発者向け。`U"関数名: 内容"` の形式で、パスや値を含めてよい
- `detail` が出るのは `crash.log` だけ。画面には分類に対応する文言だけが出る

## 4. 外部 API を呼ぶとき

失敗の表し方は3種類あり、いずれも黙って通る。

| 表し方 | 例 | 対処 |
|--------|-----|------|
| 例外を投げる | `Parse<T>()`、`JSON::get<T>()` | 非例外版（`ParseOpt<T>()`、`getOpt<T>()`）を使う |
| 既定値を返す | `TOMLValue::get<T>()` | 使わない。既定値を使うなら `getOr()` で明示する |
| 空のオブジェクトを返す | `Texture`、`Audio` の生成 | `isEmpty()` で確認する |

非例外版のない API に限り、`try-catch` で包んで `expected` に変換する関数を書く。
その関数の `try` には、その API の呼び出しだけを置く。

## 5. 生成が失敗しうるとき

コンストラクタでは失敗しうる処理を行わない。失敗しうる生成は `expected` を返す
静的メンバ関数に置く。

```cpp
struct Config
{
    double volume;
    Size resolution;

    [[nodiscard]] static std::expected<Config, String> Load(FilePathView path);
};
```

- コンストラクタは受け取った値を格納するだけにする
- メンバの生成が失敗しうる場合も同じ形にし、その関数の中で組み立てる

## 補足

### Main() の実装で守ること

- ゲーム本体は別関数に切り出し、`Main()` 直下にデストラクタを持つ変数を置かない
- 捕捉するのは `FatalError` / `s3d::Error` / `std::exception` / `...` の4つ
- `FatalError` 以外は `FatalReason::Unknown` として扱う
- 記録・表示のあと `std::_Exit(EXIT_FAILURE)` で終了する
- 記録・表示は失敗しても無視する
- Debug では画面に出さず、`crash.log` と Console に出す

### Main() の実装の根拠

ゲーム本体を別関数に切り出す理由。

- `std::_Exit()` は自動変数のデストラクタを走らせない。catch に入った時点で
  ゲームのオブジェクトを破棄済みにするため、`Main()` 直下に生存させない

`std::exit()` ではなく `std::_Exit()` を使う理由。

- `std::exit()` は静的オブジェクトの破棄と s3d のスレッドが噛み合い、プロセスが
  終了しなくなる（実測で確認）
- `std::_Exit()` は出力のフラッシュも行わないため、呼ぶ前に明示的に流す

記録・表示が失敗しても無視する理由。

- この時点では、失敗を伝える先も回復手段もない

`s3d::Error` を捕捉する理由。

- s3d は `Error` 系を投げる（`Parse<T>()`、`JSON::get<T>()` など）。ただしこれらは
  非例外版があり、4章で避ける。捕捉が実際に効くのはエンジン内部の `EngineError` に対してで、
  日常的に通る経路ではなく保険と位置づける
- `s3d::Error` は `std::exception` を継承していないため、`std::exception` の catch では
  取りこぼす

Debug で画面に出さない理由。

- `/run` による自動実行が、モーダルな表示で停止するため

### 1章の根拠

失敗を値で伝える理由。

- 失敗がシグネチャに現れ、扱い忘れを `[[nodiscard]]` で検出できる
- 例外は途中の層を素通りするため、どこで捕まえるべきかがコードから読み取れない
- s3d の `Error` は `String` のメッセージと種別名しか持たず、呼び出し側が分岐するための
  情報がない。表示して終了するための型であり、回復のための型ではない

終了を決めるのを受け取った側に限る理由。

- 下位の関数が終了を決めると、呼び出し側が回復を選べなくなる。同じ読み込み関数を、
  起動時は「失敗したら終了」、ホットリロードは「旧データを維持して続行」の
  両方で使えるようにする
- 「終了させたい失敗か」は主観で判定できないが、「この関数は `expected` を返せるか」は
  コードの形から答えられる

ゲームループ内での終了を禁じない理由。

- 禁じると、`IPhase::update` や System のようにシグネチャが固定された場所で受け取った
  失敗に行き場がなくなり、握り潰すしかなくなる

### 2章の根拠

`Optional` と `expected` の境界を「正常系か失敗か」だけで決める理由。

- 「呼び出し側が理由を知る必要があるか」を同じ軸に混ぜると、同じ関数が呼び出し側の都合で
  手段を変えることになる。理由の要否は `E` の型の選択に降ろす

`E` の既定を `String` にする理由。

- `Main()` が必要とするのは `detail` の文字列だけで、分類（`FatalReason`）は終了を決める側が
  文脈から選ぶ。下位が `enum class` を用意しても `Main()` では使われない

### 3章の根拠

文言を投げる側に書かせず分類だけ渡させる理由。

- リリース版で内部の詳細を出さないことを、書く人の注意ではなく通り道の構造で保証する
- プレイヤーに見せる文章が1箇所に集まり、口調と粒度が揃う

直接終了せず投げる理由。

- デストラクタが走り、書きかけのファイルや s3d のリソースが後始末される
- 記録・表示・終了コードの経路が1本になる
- テストから `REQUIRE_THROWS_AS` で検証できる（直接終了するとテストランナーごと落ちる）

`FatalError` を `s3d::Error` から派生させない理由。

- 指示付き初期化を使うにはアグリゲートである必要があり、基底クラスを持てない
- 派生していなければ `s3d::Error` と無関係な型になり、catch の順序を誤って
  吸われる事故が起きない

### 4章の根拠

「例外を投げない関数を選ぶ」だけでは足りない理由。

- 既定値を返す版と空のオブジェクトを返す版は、例外を避けても失敗が検出できないまま通る。
  3種類すべてを境界で潰す必要がある

`get<T>()` を禁じ `getOr()` は認める理由。

- `get<T>()` は頼んでいない既定値を黙って返すため、失敗と正常な値を区別できない。
  `getOr()` は呼び出し側が代替値を明示しているので、失敗の握り潰しにあたらない

変換関数の `try` に API の呼び出しだけを置く理由。

- 範囲を広げると、変換の対象でない例外まで `expected` に潰れる

### 5章の根拠

コンストラクタで失敗しうる処理を行わない理由。

- コンストラクタには失敗を返す手段がなく、投げるしかない。「失敗は値で伝える」を守れない

コンストラクタを非公開にせず、静的メンバ関数を足すだけにする理由。

- 非公開にするとアグリゲートでなくなり、指示付き初期化が使えない。
  読み込みを経ずに値から直接組み立てる道を、テストのために残す
