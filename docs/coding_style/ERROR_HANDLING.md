# ERROR_HANDLING.md

エラー処理の規範。

## 1. 原則

`throw` は開発者への原因調査の依頼である。

- 投げられた例外はすべて記録され、調査の対象になる
  - 正常なテストプレイで記録が0件であることを目指す
  - 内部で `throw` を行う外部ライブラリの使用を控える
- 投げる側は「何が失敗したか」だけを伝える。原因がバグか外部要因かは考えない
- 投げられた例外は途中で `catch` せず、ゲームを終了させる
- 正常系で起こる、調査の要らない無効値には `throw` を使わない

意図: 想定外の挙動をすべて、投げた瞬間のスタック付きで拾う。
失敗したまま動き続けさせず、終了させて調査する。
戻り値で伝えると失敗が途中で埋もれやすく、途中の関数すべてに伝播の分岐が要る。

## 2. 手段の選び方

| 状況 | 手段 |
|------|------|
| 正常系で起こる「値がない」状態 | `Optional<T>` |
| それ以外（失敗、不変条件・呼び出し契約の違反） | `throw` |

- `assert` は使わない（Release で確認が消え、違反したまま動き続けるため）
- `Optional` を返す関数には `[[nodiscard]]` を付ける

## 3. 投げるとき・受けるとき

`Error` を投げる。

```cpp
throw Error{U"アニメーションのクリップのファイルを開けない"};
```

- メッセージには、何が想定と違ったかを書く。調査の出発点になる
- 原因の推測と、スタックやローカル変数で分かること（関数名・引数の値）は書く必要がない
- `catch` は `Main` にだけ書き、すべての例外を受けて（`catch (...)`）何もせずに終える

## 4. 外部 API を呼ぶとき

外部 API の失敗の表し方を確かめ、失敗を黙って通さない。

| API の失敗の表し方 | 対処 | 例 |
|-------------------|------|-----|
| 例外を投げる | そのまま使う | `Parse<T>()` |
| 戻り値で表す（空のオブジェクト・`bool`・`Optional` など） | 確かめて、失敗なら `throw` する | `Texture` の `isEmpty()`、`TOMLReader` の `isOpen()` |
| 失敗を見分けられない（頼んでいない既定値を返すなど） | 使わない | `TOMLValue::get<T>()` |
| 失敗していないのに内部で例外を投げる | 使わない | cpptoml の一部の API |
