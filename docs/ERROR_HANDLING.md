# ERROR_HANDLING.md

エラー処理の使い分け規範。
「その失敗は誰のせいか」「呼び出し側は何を知る必要があるか」で手段を選ぶ。

## 判断手順

1. その失敗はコードのバグでしか起きないか → `assert`
2. 「値がない」ことが仕様上ありえる正常な結果か → `Optional<T>`
3. それ以外の失敗 → `std::expected<T, E>`（第一候補）
4. `expected` の失敗を致命として確定させる初期化経路の最上位層、
   または `expected` を返せないコンストラクタ内か → `throw Error{...}`（最後の手段）

---

## assert — プログラマのバグ

コードが正しければ決して偽にならない条件（不変条件・呼び出し契約）の検証に使う。

- `assert(条件 && "日本語メッセージ")` の形式で、違反時に原因が分かるメッセージを添える
- リリースビルドでは消える。**外部入力・設定ファイル・ユーザー操作の検証には使わない**

## Optional<T> — 「値がない」が正常系

失敗ではなく「該当なし」を表す。呼び出し側が理由を知る必要がない場合に使う。

- s3d の `Optional<T>` を使う（`std::optional` は使わない）
- 返り値に使う関数には `[[nodiscard]]` を必須とする

## std::expected<T, E> — 理由つきの失敗（第一候補）

「値がない」で表せない失敗はこれで返し、失敗の扱いを型で呼び出し側に強制する。
読み込み・パースの下位関数は、失敗しても throw せず `expected` で返す。

- C++23 標準。s3d に相当型がないため、ここだけ std を使う（**s3d 優先ルールの例外**）
- 返り値に使う関数には `[[nodiscard]]` を必須とする
- エラー型 `E` は表示・ログ用途なら `String`、呼び出し側が分岐するなら専用の `enum class`

## throw Error — 最後の手段

書いてよいのは、初期化・アセット/設定読み込みの経路のうち、次のいずれかに限る。

- 下位から `expected` で伝播してきた失敗を致命として確定させる**最上位の層**
- コンストラクタ内など、**`expected` を返せない箇所**

守ること：

- ゲームループ内（毎フレーム実行される `Phase::update` / System）では投げない
- 新たに throw を書くときは、`Optional` / `expected` で表現しない理由を
  Why not コメント（[COMMENT.md](COMMENT.md) 参照）として添える
- s3d の `Error` を使い、メッセージは `U"関数名: 内容"` の形式（日本語可）

### 捕捉は Main() に一元化する

throw は「致命の確定」なので、途中の層に回復手段は定義上存在しない。
致命エラーの捕捉点は `Main()` の一箇所のみとする。

外部 API の失敗を拾うときは、まず**例外を投げない関数を選ぶ**
（例：s3d の TOML は `get<T>()` ではなく `getOpt<T>()`。`get<T>()` は失敗時に
既定値を黙って返すため、失敗の検出には使えない）。

その上で、途中の層に `try-catch` を書いてよいのは次の二つに限る。

- **変換**：例外を投げる API を `expected` を返す関数に包む境界で、例外を `unexpected` に
  変換する。非例外系の代替が存在しない API に限る
- **定義された回復**：失敗時の挙動が仕様として決まっている場合
  （例：デバッグ時の設定ホットリロード失敗 → 旧設定を維持してログを出す）

回復を定義せず、ログだけ出して続行する catch（握り潰し）は書かない。

---

なお、ゲームループ内の関数は例外を投げない前提だが、`noexcept` 指定の義務は課さない
（EnTT・s3d の呼び出しを含む関数で厳密に保証するコストが見合わないため）。
