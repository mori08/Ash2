# 単体テストの原則

テストの作成・レビュー・仕分けの判断に使う。
書き方・実行方法は [TEST.md](TEST.md) を参照。
出典: Vladimir Khorikov『単体テストの考え方／使い方』の枠組み。

## テストの価値は4本柱の積

1. リグレッションからの保護 — 本物のバグを捕まえる
2. リファクタリングへの耐性 — 挙動を変えない変更で壊れない（偽陽性を出さない）
3. 迅速なフィードバック — 速く回る
4. 保守のしやすさ — 読めて、壊れたとき原因がすぐ分かる

積で決まるため、1つでも 0 に近ければそのテストの価値は 0 に近い。
①と②はトレードオフしない。両立を壊す唯一の原因は実装詳細のテスト。

## 観察可能な振る舞いをテストし、実装詳細をテストしない

判定基準は「内部だけを変えて挙動を保ったとき、このテストは壊れるべきか」。
壊れるべきでないものに結合しているテストは作り直す。

以下は典型例であり、基準そのものではない。例と基準が食い違ったときは基準を採る。

- 検証対象は、公開 API を通じて外から観測できる入力に対する出力・状態変化
- private メソッド・内部の呼び出し順序・生成手順・内部表現には結合しない
- mock の call_args による「呼ばれたこと」の検証は実装詳細
	- 操作後の実状態を読み直して検証する
- private を直接テストしたくなったら設計のサイン
	- 公開経路から検証するか、隠れた責務を切り出す

## 依存の分類とモック方針

| 依存 | このプロジェクトでの例 | 方針 |
|---|---|---|
| プロセス内 | System のロジック、Config のパース、値の変換 | モックしない |
| プロセス外・管理下 | 設定ファイル（`Ash2/App/assets/config/*.toml`） | 実ファイルは読まず、パーサに文字列を直接渡す |
| プロセス外・管理外 | 描画、アセット、入力デバイス、時刻、乱数 | テスト対象から切り離す |

- 管理外依存は「切り離しにくい」のではなく、テスト実行時には存在しない（[TEST.md](TEST.md)）
- 管理外依存はモックで差し替えるのではなく、引数で受け取る形にして切り離す
	- 時刻は `Scene::DeltaTime()` を `Main()` の1箇所だけで取得し、以降は `FrameData` の
	  `dt` として渡す。乱数を使うときも同様に `FrameData` へ切り出す
	- 管理外依存に触れる処理と純粋な計算が同じ関数にある場合は、計算を関数に切り出し、
	  切り出した側だけをテストする
- 設定ファイルを実物で読まないのは、ファイルの中身が調整値であるため
	- 検証したいのはパースの仕様であって調整値ではない。実ファイルを読むと調整のたびに壊れる
	- 全フィールドを含む正常系を1つと、必須キーが欠けたときに `Error` を投げる異常系を書く
- モックライブラリは導入していない

## テストの単位は振る舞い

- 1テストは1つの観察可能な振る舞い（入出力・状態遷移）を検証する
- メソッド／クラスに1対1でテストを対応させない
- テストの入口は本番と同じ公開経路を第一候補にする

## 既存テストの仕分け rubric

上から順に判定する。

1. 実装詳細に結合している → 作り直す
2. assert が観察可能な状態を捉えていない → 強化する
3. 管理外依存を偽物で埋めて検証している → 純粋な計算を切り出し、切り出した側をテストする
4. 何も検証していない・重複している → 削除するか集約する

## 量の管理

- テストがあること自体は価値ではない
- 総数やカバレッジ % を KPI にしない
	- 見るのは偽陽性の発生（正しいリファクタで壊れた回数）とバグ捕捉の実績
- カバレッジは目標値ではなく、未カバー箇所を見つける診断に使う
- 価値 0 と判定したテストの削除は、追加と同格の貢献として扱う
