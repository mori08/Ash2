```
## 調査してほしいこと
- `gh issue view <number>` でIssueの内容・ラベル・コメントを確認
- `docs/ARCHITECTURE.md` で設計方針・レイヤー構成を確認
- `docs/REFERENCE.md` で関連する既存のコンポーネント・システム・フェーズを確認
- `docs/game_design/` 配下の関連ドキュメント（battle_design.md・motion_design.md 等）でゲームデザイン仕様との整合を確認
- 変更が必要なファイルと該当箇所
- 関連するクラス・関数・コンポーネント
- 影響範囲（呼び出し元・呼び出し先）

## 文章スタイル

plan は読み物ではなく、1行ずつレビューされる文書です。
原則: 区切り（改行・箇条書き・小節）は意味の切れ目にのみ置き、その位置は書き手が制御する。

- 1行1主張: 箇条書き1項目は、単独で検証できる主張1つを1〜2文で書く。2文目は補足のみ
- 地の文の段落は「結論」セクションだけで使い、3行以内に収める。他は箇条書きと見出しで構造化する
- 理由は主張と同じ文に混ぜない。子項目に添えるか、短ければ文末の「（理由: 〜）」1つで添える
- 同種の項目は同じ雛形・同じ語順で書き、括弧の入れ子は使わない
- 箇条書きが縦に7項目を超えて続く場合は、小見出しで意味の塊ごとに区切る
- 3つ以上の列挙は文中に並べず、子項目に分ける
- 全角40字相当を超える行は、列挙か複数主張が混ざっているサインとして分割を検討する
- コード例（定義・前後差分）で示す方が散文より短く正確な箇所には、コードブロックを添える

## レポートのフォーマット

以下の形式でレポートを返してください（ファイルへの書き出しは不要です）。
上記の文章スタイルに従ってください。

# plan-<number>

## 結論
<何をどこまでやるか。3行以内の地の文。変更が1ファイルならここに含める>

## 判断

**<論点>**
- <判断>
  - <理由・補足。1行1文で、複数あれば行を分ける>
- <同じ論点で判断した内容が他にもあれば並べる>

<論点ごとに太字の小節を立てる>
<検討のうえやらないと決めた事項も、判断として載せる>

## 変更ファイル一覧
<変更が複数ファイルに及ぶ場合のみ。1ファイルなら結論に書きこのセクションは省略>
- `<ファイルパス>`: <変更内容を1行で>

## 手順
1. <手順。順序に理由がある場合は1行で添える>

<手順が多い場合はビルドが通る単位の段階でグループ化し、段階ごとに見出しを付ける>

## 注意点
<実装時の行動が変わる項目のみを箇条書きで>

## 影響なしと確認済み
<テスト・ドキュメント・ビルド設定などへの非影響を、根拠つきで1行ずつ>
```

### 2. レポートの整形とプランファイルの書き出し

Plan エージェントのレポートを Agent ツール（`subagent_type: format-doc`）で整形する。
プロンプトには「文章スタイル」セクションの全文と、レポート本文を含める。

整形後のレポートをもとに、親が `tmp/plan-<number>.md` を作成する。

作成後、Bash で `code tmp/plan-<number>.md` を実行してファイルを IDE で開く。

その後、クリッカブルなリンクでユーザーに提示する。

```
計画を記録しました → [plan-<number>.md](tmp/plan-<number>.md)
```

計画の概要（結論・主要な判断・注意点）をその場でも要約して伝える。

### 3. レビューループ

**ユーザーの明示的な承認を得るまでこのループを続ける。**

ユーザーからのフィードバックの種類に応じて以下を使い分ける。

| フィードバックの種類 | 対応 |
|---|---|
| 計画の修正・方針変更 | Agent ツール（`subagent_type: Plan`、`model: opus`）を再起動し、現在のプランファイルの内容と修正点を渡してレポートを返させる。受け取ったレポートをもとに親がプランファイルを上書きする |
| コードベースへの質問（「〇〇はどこで使われてる？」など） | Agent ツール（`subagent_type: Explore`）を起動して調査し、結果をユーザーに伝える |
| 軽微な文言修正 | 親が直接プランファイルを編集する |

Plan 再起動時のプロンプト例：

```
現在の計画を以下に示します。修正点を反映した計画をレポートとして返してください
（ファイルへの書き出しは不要です）。文章スタイルは元の指示と同様、1行1主張・
地の文の段落は結論のみ・箇条書き各項目は1〜2文で書いてください。
フォーマットも元の指示と同じ構成（結論・判断・手順・注意点・影響なしと確認済み）を守ってください。

## 現在の計画
<プランファイルの内容>

## 修正点
<修正点>
```

承認後、次フェーズ（implement-issue）へ進む。
