# plan-issue

Issue の仕様を上位の判断から順に段階的に議論して決め、実装の段取りをまとめて承認まで進める。

## 記録先

| 記録先 | 内容 |
|---|---|
| `tmp/plan-<number>.md` | 各段階の結論と段取り |
| Issue 本文 | 仕様の結論 |

プランファイルは `docs/work_style/PLAN_FORMAT.md` の規約に従って書く。

## 手順

### 1. 調査

Agent ツール（`subagent_type: Explore`）を起動し、以下を調べさせる。

- `gh issue view <number>` の内容・ラベル・コメント
- `docs/ARCHITECTURE.md` の設計方針・レイヤー構成
- `docs/REFERENCE.md` の関連する既存のコンポーネント・システム・フェーズ
- `docs/game_design/` 配下の関連するゲームデザイン仕様
- 変更が必要なファイルと該当箇所
- 関連するクラス・関数・コンポーネントと、その呼び出し元・呼び出し先
- コード全体の `TODO(#<number>)`

### 2. 段階的な議論

仕様を上位の判断から順に段階に分けて議論する。
段階の数と名前は Issue に合わせて決める。

| 段階の例 | 決めること |
|---|---|
| 大枠 | 実現すること・範囲・基本方針 |
| 構成 | 責務の分担・部品の分け方・データの形 |
| 細部 | 名前・境界条件・例外の扱い |

各段階で以下を行う。

1. その段階の論点だけを提示する
2. 論点ごとに選択肢・推奨・理由を示し、ユーザーと議論して決める
3. 段階の結論をプランファイルの `## § <段階名>` に書き込み、ユーザーに提示する
   - 採用した内容に加え、見送った選択肢とその理由を書く

次の段階の論点は、前の段階の結論を書き込んでから出す。
判断が自明な段階は、一言の確認で済ませる。

下位の段階で上位の判断に問題が見つかったら、上位の段階に戻って決め直す。
決め直した段階の節を書き換え、影響を受ける下位の段階を見直す。

コードベースへの質問は Agent ツール（`subagent_type: Explore`）で調べて答える。

### 3. Issue 本文への反映

仕様の段階をすべて終えたら、各段階の結論を Issue 本文に反映する。
反映する文面をユーザーに提示し、承認を得てから `gh issue edit <number> --body-file <file>` で更新する。

### 4. 段取り

プランファイルに以下の節を書き、ユーザーの明示的な承認を得る。

| 節 | 内容 |
|---|---|
| `## § 手順` | 変更対象のファイルと、実装の順序を番号付きリストで書く。変更箇所が特定できる手順には対象箇所のパスを添える。手順が多い場合はビルドが通る単位でグループ化する。`TODO(#<number>)` があれば削除を含める |
| `## § 注意点` | 実装時の行動が変わる項目のみを書く |
| `## § 影響` | 影響がある箇所（呼び出し元・テスト等）と、影響なしと確認した箇所を根拠つきで書く |

承認後、次フェーズ（implement-issue）へ進む。
