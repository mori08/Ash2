# plan-issue

Plan サブエージェントに調査と計画を委ね、ユーザーのレビューと議論を経て承認まで進める。

## 手順

### 1. Plan サブエージェントで調査・計画

Agent ツール（`subagent_type: Plan`、`model: opus`）を起動し、以下を渡す。

```
Issue #<number> の実装計画を立ててください。

## 調査してほしいこと
- `gh issue view <number>` でIssueの内容・ラベル・コメントを確認
- `docs/ARCHITECTURE.md` で設計方針・レイヤー構成を確認
- `docs/REFERENCE.md` で関連する既存のコンポーネント・システム・フェーズを確認
- `docs/game_design/` 配下の関連ドキュメント（battle_design.md・motion_design.md 等）でゲームデザイン仕様との整合を確認
- 変更が必要なファイルと該当箇所
- 関連するクラス・関数・コンポーネント
- 影響範囲（呼び出し元・呼び出し先）
- `TODO(#<number>)` をコード全体から検索し、該当があれば削除を計画に含める

## 文章スタイル

`docs/PLAN_FORMAT.md` を読み、その規約に従って書いてください。

## レポートのフォーマット

以下の形式でレポートを返してください（ファイルへの書き出しは不要です）。
`<>` 内は各セクションに何を書くかの説明です。
各セクションの中身は docs/PLAN_FORMAT.md の規約に従って書いてください。

# plan-<number>

## § 実装方針

<何をどうやって実現するか。
採用した設計とその理由に加え、検討のうえ見送った選択肢も書く。
変更対象のファイルもここに列挙する>

## § 手順

<実装の順序を番号付きリストで書く。
変更箇所が特定できる手順には、対象箇所のリンクを添える。
手順が多い場合はビルドが通る単位の段階でグループ化する>

## § 注意点

<実装時の行動が変わる項目のみを書く>

## § 影響

<変更の影響範囲。
影響がある箇所（呼び出し元・テスト等）と、影響なしと確認した箇所（根拠つき）の両方を書く>
```

### 2. プランファイルの書き出し

Plan エージェントのレポートをもとに、親が `tmp/plan-<number>.md` を作成する。

作成後、Bash で `code tmp/plan-<number>.md` を実行してファイルを IDE で開く。

その後、クリッカブルなリンクでユーザーに提示する。

```
計画を記録しました → [plan-<number>.md](tmp/plan-<number>.md)
```

計画の概要（実装方針の要点・注意点）をその場でも要約して伝える。

### 3. レビューループ

**ユーザーの明示的な承認を得るまでこのループを続ける。**

ユーザーからのフィードバックの種類に応じて以下を使い分ける。

| フィードバックの種類 | 対応 |
|---|---|
| 計画の修正・方針変更 | Agent ツール（`subagent_type: Plan`、`model: opus`）を再起動し、現在のプランファイルの内容と修正点を渡してレポートを返させる。受け取ったレポートをもとに親がプランファイルを上書きする |
| コードベースへの質問（「〇〇はどこで使われてる？」など） | Agent ツール（`subagent_type: Explore`）を起動して調査し、結果をユーザーに伝える |
| 軽微な文言修正 | 親が直接プランファイルを編集する |

Plan 再起動時のプロンプト例：

```
現在の計画を以下に示します。修正点を反映した計画をレポートとして返してください
（ファイルへの書き出しは不要です）。文章スタイルは `docs/PLAN_FORMAT.md` の規約に
従ってください。フォーマットも元の指示と同じ構成
（§ 実装方針・§ 手順・§ 注意点・§ 影響）を守ってください。

## 現在の計画
<プランファイルの内容>

## 修正点
<修正点>
```

承認後、次フェーズ（implement-issue）へ進む。
