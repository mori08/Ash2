---
name: meta-review
description: Review skills, rules, agents, and docs for staleness or inconsistencies with the actual codebase, then optionally create GitHub Issues. Targets meta-information (skills/rules/agents/docs) — not code quality or bugs (use full-review for those).
---

プロジェクトのメタ情報（スキル・ルール・エージェント・ドキュメント）を読み、
コードの実態との乖離・陳腐化・矛盾を報告する。
最終的にユーザーが選択した項目を GitHub Issue として登録する。

> **対象範囲**: コードの品質・バグではなく、スキル・ルール・エージェント・ドキュメントの整合性。
> コードレビューは `full-review` スキルを使うこと。

## 手順

### 1. ベースラインの把握

以下を並列で読む（`docs/ARCHITECTURE.md` と `docs/REFERENCE.md` はここで読む。ステップ 2 では除外する）。

- `CLAUDE.md`
- `docs/ARCHITECTURE.md`
- `docs/REFERENCE.md`
- `.claude/rules/` 以下の全ファイル
- `.claude/skills/` 以下の全ファイル
- `.claude/agents/` 以下の全ファイル（サブフォルダを含む）

### 2. ドキュメントの走査

`docs/` 以下の全ファイルを Glob で列挙し、`ARCHITECTURE.md` と `REFERENCE.md` を除いてすべて読む
（両ファイルはステップ 1 で読み済み）。

### 3. コードのサマリ取得

サブエージェントを 1 つ起動し、以下を指示する。

**指示内容（プロンプトに全文転記すること）：**

```
Ash2/src/ 以下の .hpp / .cpp を Glob で列挙してすべて読む。
ドキュメント・スキル・ルール等は読まない。

以下の観点でサマリを返す。各項目は箇条書きで、全体を 600 トークン以内に収めること。

- 実際に使われているディレクトリ構造（Ash2/src/ 直下のサブフォルダ名のみ）
- 主要クラスの名前と役割（最大 15 件）
- 定着しているコーディング慣習（ルールに書かれていなくても繰り返し現れるパターン、最大 10 件）
- テストフレームワーク・ビルドシステム・外部ライブラリ等のツールチェーン
```

### 4. チェックの実施

ステップ 1〜3 で得た情報をもとに、以下の観点でチェックする。
命令用 Markdown（CLAUDE.md・rules・skills・agents）全般については、`.claude/rules/instruction-md.md` の指針に従っているかも確認する。

#### rules のチェック

- ルールに記載された規約がコードで実際に守られているか（ルール → コード方向）
- コードで定着している慣習がルールに記載されていないか（コード → ルール方向）
- 複数の rules ファイル間で矛盾する記述がないか

#### skills のチェック

- スキル内で参照しているファイルパス・ディレクトリが実際に存在するか
- スキルの手順がプロジェクトの現状に合っているか
  （例：参照しているツール・コマンド・ファイル名が変わっていないか）
- スキル間で重複・矛盾する手順がないか

#### agents のチェック

- `description` の内容がコードの実態・アーキテクチャと合っているか
  （description は Claude がエージェントへの委譲判断に使うため、ずれがあると意図しない呼び出しや呼び出し漏れが起きる）
- エージェント内で参照しているファイルパス・コマンドが実際に存在するか
- 同じ責務を持つエージェントが重複定義されていないか
- agents と skills の間で手順・責務が矛盾していないか

#### settings.json のチェック

- hooks に登録されているコマンド・スクリプトが実際に存在するか
- permissions（allow / deny）の設定がプロジェクト構成と合っているか
- スキル・ルール・エージェントが前提とする設定と食い違っていないか

#### docs のチェック

`docs/ARCHITECTURE.md` / `docs/REFERENCE.md` とコードの整合は `full-review` が持つ。ここでは扱わない。

- コードと矛盾する記述がないか
- 存在しないファイル・クラス・コマンドを参照していないか
- 明らかに陳腐化していると判断できる記述がないか

#### CLAUDE.md のチェック

- プロジェクト全体の指示がコードの実態と合っているか
- 参照しているスキル・ルール・エージェント・パスが実際に存在するか

### 5. 発見の絞り込み

チェック結果から、重要度の高いものを **3〜5 件** に絞る。
些細な表現の揺れより、実害のある乖離・矛盾・陳腐化を優先する。

### 6. レポートの出力

以下の形式でチャットに出力する。

```
## メタレビュー結果

**1. <タイトル>**
- 対象: `<ファイルパス>`（rules / skills / agents / docs / CLAUDE.md / settings.json）
- 内容: <具体的な説明。コードのどの部分と乖離しているかを明示する>
- 提案: <修正案。可能なら修正後のテキストを示す>

**2. <タイトル>**
...
```

### 7. Issue 化の確認

レポート出力後、以下のように尋ねる。

```
Issue 化したい項目があれば番号で教えてください（例: 1 3）。
不要であれば「なし」と入力してください。
```

ユーザーが番号を指定した場合、各項目について `create-issue` スキルを使って GitHub Issue を作成する。

- ラベルは `chore` を基本とし、実害のある乖離は `bug` を使う
- タイトルは日本語で（GIT.md の規則に従う）
- 本文にはレポートの「内容」と「提案」を含める
